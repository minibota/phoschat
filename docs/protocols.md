# Protocols and upstream dependencies

Research checked on 10 November 2026. This document records provider choices, deployment constraints, and the boundary of the v0.2 preview.

## Desktop foundation

Qt 6.12.0 is the current Qt LTS release and 6.11.3 is also within upstream standard support. The project's build floor is declared in `CMakeLists.txt` and targets the Qt Base APIs actually used. A release bundle should use a patched Qt build and verify the SQLite driver, platform plugin, and TLS backend on each target OS. Qt Network can use a native backend such as Schannel or Secure Transport, or an OpenSSL backend, depending on how Qt was built. [Qt release matrix](https://doc.qt.io/qt-6.12/qt-releases.html) · [Platform support](https://doc.qt.io/qt-6.12/supported-platforms.html) · [Qt TLS documentation](https://doc.qt.io/qt-6/ssl.html)

The Qt Base modules used here are available under LGPL-3.0. A binary distribution that bundles LGPL Qt must meet its license, notices, source availability, and user replacement requirements. Review those duties against the exact release package, including its TLS backend and other third-party components. SQLite is in the public domain. Qt Network Authorization is GPL-3.0 under the open-source Qt license, so evaluate that dependency separately before using it in a future OAuth adapter. [Qt module licensing](https://doc.qt.io/qt-6/licensing.html) · [Qt LGPL obligations](https://www.qt.io/development/open-source-lgpl-obligations) · [SQLite copyright](https://www.sqlite.org/copyright.html)

QtKeychain provides asynchronous Qt jobs for macOS Keychain, Windows Credential Manager, and Linux desktop keyrings. Its modified BSD license applies to redistribution. An unavailable or locked keyring must fail closed or offer an explicitly session-only secret. Persist provider settings and account IDs separately from secrets. [QtKeychain](https://github.com/frankosterfeld/qtkeychain)

`QSystemTrayIcon` is sufficient for the initial tray and best-effort notifications. Tray availability and balloon support depend on the desktop, and unread counts and errors should remain visible in the application. Future native notification backends can use the XDG notification portal, macOS UserNotifications, and Windows App SDK app notifications, with separate tests for permission and activation. [Qt tray API](https://doc.qt.io/qt-6/qsystemtrayicon.html) · [XDG notification portal](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Notification.html) · [Apple UserNotifications](https://developer.apple.com/documentation/usernotifications/unusernotificationcenter) · [Windows app notifications](https://learn.microsoft.com/en-us/windows/apps/develop/notifications/app-notifications/)

## IRC and IRCv3

IRC is the first provider. Each account has an independent asynchronous connection. The adapter owns registration, nick and channel normalization, protocol errors, and reconnect behavior. The core owns conversation identity and local message persistence. A disconnected client only has the messages it previously received or sent, unless a server supplies replay or a future adapter implements explicit history requests.

The classic message section is limited to 512 bytes including CRLF. IRCv3 provides a separate incoming tags section of up to 8191 bytes, including delimiters. Client-supplied tag data has a 4094-byte limit before delimiters. Parse frames before decoding text, account for fragmented socket reads, and validate outgoing commands against line breaks and encoded byte length. Channel and nick comparison follow the server's advertised `CASEMAPPING`. [Modern IRC client protocol](https://modern.ircdocs.horse/) · [IRCv3 message tags](https://ircv3.net/specs/extensions/message-tags.html)

`CAP LS 302` allows the adapter to discover capabilities before completing registration. SASL PLAIN carries a reusable secret and requires verified TLS. Split its base64 payload into `AUTHENTICATE` chunks of at most 400 bytes and send the terminator required for an exact multiple of 400. A configured SASL account should receive a clear error if the server cannot authenticate it. `server-time` supplies the server timestamp for a received message, and `msgid` can be used for deduplication when present. A successful local write does not imply remote delivery or a read receipt. [CAP negotiation](https://ircv3.net/specs/extensions/capability-negotiation.html) · [SASL v3.1](https://ircv3.net/specs/extensions/sasl-3.1.html) · [SASL v3.2](https://ircv3.net/specs/extensions/sasl-3.2.html) · [Server time](https://ircv3.net/specs/extensions/server-time.html) · [Message IDs](https://ircv3.net/specs/extensions/message-ids.html)

Explicit remote history is a separate capability and remains pending. The IRCv3 draft uses `draft/chathistory` with `BATCH` and timestamp or message-ID references. A future implementation must distinguish replay from live updates, avoid notifications for replay, and avoid creating false membership changes. `echo-message` can be added once outgoing messages can be reconciled with server echoes without duplicating the timeline. IRC offers no general global presence or delivery acknowledgement in the MVP. [Chat history draft](https://ircv3.net/specs/extensions/chathistory.html) · [Batch](https://ircv3.net/specs/extensions/batch.html) · [Echo message](https://ircv3.net/specs/extensions/echo-message.html)

## Telegram preview

The implemented preview dynamically loads the official TDLib JSON interface. The runtime floor is 1.8.38. See [Telegram setup](telegram.md) for tested versions and account onboarding. Homebrew lists 1.8.0 as its stable packaged version, while TDLib upstream publishes no GitHub Releases and its active source line reached 1.8.70. The JSON ABI and the request/update schema have different compatibility guarantees. Pin a tested upstream commit and its exact API schema, and verify all three platforms before shipping. TDLib uses Boost Software License 1.0 and builds with OpenSSL, zlib, and `gperf`. [Upstream build and license](https://github.com/tdlib/td) · [Upstream history](https://github.com/tdlib/td/commits) · [Release listing](https://github.com/tdlib/td/releases) · [Homebrew package](https://formulae.brew.sh/formula/tdlib)

Run a single ordered `td_receive` loop on a worker and route events by TDLib client ID. Copy received payloads before their TDLib-managed lifetime ends. Use authorization updates to drive phone, code, email, or 2FA screens as requested by the server. Configure a separate TDLib database and files directory per account. Derive a per-account database key from the API hash and account ID when persistent credentials are enabled. Treat TDLib session data separately from PhosChat history. [TDLib JSON interface](https://core.telegram.org/tdlib/docs/td__json__client_8h.html) · [TDLib authorization and updates](https://core.telegram.org/tdlib/getting-started)

Developers can obtain an `api_id` and `api_hash` from **API development tools** at `my.telegram.org`. Supply these through local configuration when testing and keep private values out of version control and logs. A distributed integration needs its own application ID and must disclose that it uses the Telegram API. Channel access requires support for official sponsored messages. Enable channels only after implementing and validating that behavior. Start with cloud direct and group conversations. Secret chats have a separate TDLib option and need a distinct UI, lifecycle, and persistence policy before enabling support. [Creating a Telegram application](https://core.telegram.org/api/obtaining_api_id) · [Telegram API terms](https://core.telegram.org/api/terms) · [TDLib authorization parameters](https://core.telegram.org/tdlib/getting-started)

## Slack preview

Use official Web API and Events API endpoints. Slack's public-client OAuth PKCE flow became generally available in March 2026. The preview uses a registered localhost redirect URI and exchanges the authorization code without an embedded client secret. It polls the last opened conversation and respects rate limits. See [Slack setup](slack.md). Validate `state`, keep the verifier short-lived, and support secure refresh token rotation. The adapter handles rotating tokens and supports approved existing user tokens. [Slack PKCE guide](https://docs.slack.dev/authentication/using-pkce/) · [PKCE release note](https://docs.slack.dev/changelog/2026/03/30/pkce/)

Use user-scoped grants to test a user-facing client. Workspace installation and approval policies, token type, conversation membership, and granted scopes define available operations. For discovery and reading, map the minimum `channels`, `groups`, `im`, and `mpim` scopes to the selected conversation types. Request `chat:write` only for sending. Bot tokens see conversations available to the bot and post under its identity, so pilot the actual user workflow against user tokens. Slack `ts` values are identifiers and must retain their original string representation. [Slack token types](https://docs.slack.dev/authentication/tokens/) · [History](https://docs.slack.dev/reference/methods/conversations.history/) · [Thread replies](https://docs.slack.dev/reference/methods/conversations.replies/) · [Posting](https://docs.slack.dev/reference/methods/chat.postMessage/)

For new commercially distributed off-Marketplace apps and new installations in that category, Slack documents one call per minute and at most 15 items for each of `conversations.history` and `conversations.replies`. Its clarification exempts internal customer-built apps, and it says existing unlisted installations were grandfathered. Respect `Retry-After`, paginate on demand and expose partial history. Slack's terms require a separate agreement for commercial distribution, typically via Marketplace approval, and constrain retention and bulk export of workspace data. Treat permissions, retention, revocation, and distribution approval as product gates. [Slack rate-limit change](https://docs.slack.dev/changelog/2025/05/29/rate-limit-changes-for-non-marketplace-apps/) · [Internal app clarification](https://docs.slack.dev/changelog/2025/06/03/rate-limits-clarity/) · [Distribution guide](https://docs.slack.dev/app-management/distribution/) · [Slack API terms](https://slack.com/terms-of-service/api)

Socket Mode uses an app-level credential to open the WebSocket and is suitable to evaluate with an internal workspace. Socket Mode apps are currently ineligible for public Marketplace listing. A potential Marketplace release would evaluate a signed HTTPS Events API receiver, including opt-in routing, tenant isolation, and disconnect behavior. Keep app-level and signing secrets off distributed desktops. [Socket Mode](https://docs.slack.dev/apis/events-api/using-socket-mode/) · [Events API](https://docs.slack.dev/apis/events-api/) · [Request signatures](https://docs.slack.dev/authentication/verifying-requests-from-slack/)
